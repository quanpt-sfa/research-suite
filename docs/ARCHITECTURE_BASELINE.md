# Architecture Baseline & Legacy v8.4.4 Survey

## 1. Executive Summary

This document establishes the architectural baseline of **Research Harness Suite v8.4.4** (`Reusable_Research_Harness_Suite_v8.4.4_Novelty_Semantic_Execution`) prior to refactoring into **Research Harness 9.0-dev**. 

The legacy suite provided valuable semantic execution gates, canonical hashing utilities, and stage controllers. However, its project-as-directory structure, file-based lock system, and lack of actor boundaries made it unsuitable for direct integration with external web agents (such as ChatGPT Web) and remote execution servers (Ubuntu D13).

---

## 2. Inventory of Legacy v8.4.4 Components

The legacy distribution was unpacked into `legacy_v8_4_4/Reusable_Research_Harness_Suite_v8.4.4_Novelty_Semantic_Execution`:

| Component / Subdirectory | Purpose in v8.4.4 | Assessment & v9 Strategy |
|:---|:---|:---|
| `components/state_integrity.py` | Canonical JSON serialization, SHA-256 hashing, atomic file writes (`atomic_write_file`), file locking. | **Vendored byte-for-byte** into `research_harness/legacy/v8_state_integrity.py` with SHA-256 anchor validation in `VENDORED.json`. |
| `controllers/` | Stage controllers for finding, fitting, outlining, structuring, writing. | Stateful file scripts; replaced in v9 by transactional proposal operations and dependency invalidation. |
| `audit/` | Consistency checkers for CSV registries. | Replaced by relational foreign keys, JSON schemas (Draft 2020-12), and SQLite audit triggers. |
| `templates/latex_project/` | Project skeleton with `research_harness/00_master/` CSV files. | Supported via non-destructive migration adapter `legacy/adapter.py`. |
| `release/` & `release_gate.py` | Verification gates evaluating stage status locks. | Replaced by four-dimensional status evaluation (`Integrity`, `Workflow`, `Review`, `Release`). |
| `tests/` | 105 pytest test cases verifying v8 gates, controllers, and hashing. | Preserved intact in baseline test suite. |

## 4. Architectural Gaps & Failure Modes Identified in v8.4.4

While v8.4.4 succeeded in enforcing sequential stage execution, rigorous architectural analysis revealed six fundamental vulnerabilities that necessitated the v9 Core refactor:

### Gap 1: Conflation of Cryptographic Integrity with Scientific Verification
In v8.4.4, running audit checks on an empty template project yielded:
```
STAGE 00 PASS
STAGE 01 PASS
...
AUDIT PASS
```
The system did not distinguish between "the filesystem is uncorrupted" and "valid scientific claims have been empirically verified and peer-reviewed." In v9, an empty project yields:
- `IntegrityStatus: PASS`
- `WorkflowStatus: INCOMPLETE`
- `ReviewStatus: UNASSESSED`
- `ReleaseEligibility: BLOCKED`

### Gap 2: Lack of Untrusted Gateway Boundary
v8.4.4 assumed all mutations occur via local Python scripts executing with filesystem write permissions. It provided no protocol for accepting proposals generated by external LLMs (e.g., ChatGPT Web) without giving those models direct write access or arbitrary code execution capabilities.

### Gap 3: Missing Invalidation Propagation
When an upstream proxy metric, dataset, or empirical result was revised in v8.4.4, downstream claims that relied on that metric remained marked as valid. There was no dependency graph tracking which claims were impacted by upstream revisions.

### Gap 4: HARKing Vulnerability (Hypothesizing After Results are Known)
v8.4.4 stored propositions and findings without recording whether a claim was formulated *prior* to seeing empirical results or retroactively constructed to fit observed data. In v9, the ledger enforces tamper-proof formation provenance (`CONFIRMATORY_DECLARED`, `EXPLORATORY`, `UNKNOWN`) and forbids retroactive status elevation.

### Gap 5: Absence of Actor Authentication & Independent Review
v8.4.4 had no concept of actors, tokens, or role-based authorization. Anyone running a script could mark a stage as approved. In v9, author approval is strictly separated from independent peer review, and reviewer independence policies are cryptographically enforced.

### Gap 6: File-Lock Deadlocks and Crash Inconsistency
File-based locks (`.lock` files) and distributed CSV files suffered from non-atomic updates across multiple files. A crash during migration or stage transition could leave the project in an indeterminate state. In v9, state updates are serialized inside SQLite transactions (`BEGIN IMMEDIATE` in WAL mode) paired with content-addressed artifact storage.
